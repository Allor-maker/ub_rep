# Задача: Astra A7.6 — восстановить полноценное агентное поведение

Ты подключаешься к существующему Python-проекту Astra (`nsu-budget-agent`) на openJiuwen.

Твоя роль — ведущий разработчик агентной логики. Нужно не переписать проект с нуля, а исправить фундаментальную архитектурную проблему и довести систему до состояния, в котором NeuralDeep действительно решает новые задачи.

## Контекст

В A7.5 агент достиг 46/50 на исходном наборе, но следующий набор из 50 новых задач выявил критическую проблему обобщения.

На новых задачах локально получено 12/50. При подключённом NeuralDeep и бюджете 20000 модель фактически не получила запросов: остальные задачи пропускались на предварительной стадии.

Это недопустимо для AI-агента.

Вероятная причина — сочетание предварительного распознавания семантики, политики независимой проверки и планировщика. Точную причину нужно установить по коду.

## Главный приоритет — P0

**Исправить маршрутизацию, агентный цикл и политику проверки результатов.**

Не ограничиваться расширением regex, словарей, шаблонов или обработкой нескольких конкретных формулировок.

### Требуемое поведение

1. При получении задачи сначала попробовать очевидное безопасное локальное решение.
2. Если локального решения нет — передать задачу NeuralDeep, если хватает бюджета и нет объективных ограничений безопасности.
3. NeuralDeep должна анализировать исходную инструкцию, выбирать разрешённые инструменты и получать результаты их выполнения.
4. Агент должен иметь ограниченную возможность исправлять ошибки.
5. Validator должен проверять то, что объективно проверяемо.
6. Неспособность Validator доказать правильность не должна автоматически приравниваться к ошибке.
7. Для непроверяемых результатов должна существовать явная риск-политика публикации.
8. Доказанные ошибки, запрещённые действия, нарушения файловой изоляции и некорректный формат по-прежнему должны блокироваться.
9. Действующие ограничения бюджета, журнал расходов и безопасная публикация должны сохраниться.

## Конкретные задачи

### A. Сначала провести аудит

Изучи:

- Планировщик задач и бюджетных попыток.
- LLM dispatch.
- `LLM_REQUIRE_INDEPENDENT`.
- Controller и инструментальные схемы.
- Validator и правила публикации.
- Причины `unsupported_or_unselected`.
- Различие между возможностью проверить решение и правом вызвать LLM.
- Механизмы retry и feedback.

Определи, какие проверки происходят до LLM, а какие после.

Подготовь краткую карту реального потока исполнения с точными ссылками на код.

### B. Переработать маршрутизацию

Реализуй universal LLM fallback для задач, не решённых локально.

Неизвестная формулировка сама по себе не должна запрещать модельный запрос.

Сохрани предельный расход, проверку путей, допустимых инструментов и защиту от переполнения контекста.

### C. Реализовать полноценный агентный цикл

Предпочтительная структура:

```text
OBSERVE
  → PLAN
  → TOOL CALL
  → TOOL RESULT
  → REASON / REPAIR
  → FINAL ANSWER
```

Проверь, что инструменты реально доступны модели и что модель может воспользоваться результатом предыдущего действия.

Установи ограничения на число шагов, время, расходы и повторные ошибки.

### D. Исправить Validation

Раздели состояния:

- `VERIFIED`
- `CONTRADICTED`
- `UNVERIFIED`
- `INVALID`

Не допусти подмены `UNVERIFIED` на `CONTRADICTED`.

Для непроверяемых ответов реализуй конфигурируемую конкурсную политику принятия риска.

При необходимости используй Reviewer, но не считай согласие двух LLM математическим доказательством.

Никаких необоснованных гарантий `INCORRECT=0`.

### E. Добавить регрессионные тесты

Обязательно проверь:

1. Локально решаемая задача не требует LLM.
2. Незнакомая формулировка вызывает NeuralDeep.
3. Модель получает результат инструмента.
4. Ошибка инструмента становится доступна модели для исправления.
5. Проверяемый неправильный ответ блокируется.
6. Непроверяемый ответ получает отдельный статус.
7. Политика публикации работает согласно настройкам.
8. Превышение бюджета останавливает попытки.
9. Исходные файлы не меняются.
10. Уже опубликованные ответы не перезаписываются.
11. Повторное использование модели не приводит к утечке контекста между задачами.
12. Prompt injection из файлов не может менять системные правила или расширять права инструментов.

### F. Провести тестирование

Прогони существующие unit/integration tests, Ruff, Mypy и host smoke.

Перед платными экспериментами используй MockTransport или другой безопасный тестовый транспорт.

На новых 50 задачах сначала продемонстрируй, что модель вообще вызывается и использует инструменты.

Затем, только с разрешения владельца и установленным бюджетом, проведи контролируемый live-прогон NeuralDeep.

Используй независимый grader для итоговой оценки.

Не просматривай `private_answers.json` и эталонные ответы в ходе разработки; не используй grader как источник подсказок для production-логики.

Сравни:

- Количество вызовов NeuralDeep.
- Число локальных и модельных решений.
- Correct / Incorrect / Missing / Tampered.
- Reward.
- Расход токенов.
- Причины пропусков.
- Успехи и ошибки инструментального цикла.

## P1 — блок B

Найди актуальную спецификацию блока B и установи реальный процент готовности.

Сначала закрывай требования, без которых P0 нельзя безопасно запускать.

Остальные требования блока B выполняй после стабилизации основной агентной логики.

Не объявляй блок B завершённым без матрицы требований и тестов.

## P2 — Coding

Проведи аудит текущей поддержки Coding.

После P0 и критических требований B реализуй безопасный coding workflow:

- Генерация решения.
- Изолированное исполнение.
- Запуск тестов.
- Получение ошибок.
- Исправление.
- Публикация проверенного результата.

Нельзя запускать произвольный код модели в основном процессе или с правами к секретам, исходному репозиторию и приватному grader.

## Ограничения

- Не переписывай работающие бюджетные компоненты без необходимости.
- Не отключай защиту исходных файлов.
- Не отключай проверки доказанных ошибок.
- Не добавляй ответы, завязанные на ID конкретных задач.
- Не подгоняй regex под новые 50 задач.
- Не используй эталонные ответы в production.
- Не делай commit, push или merge без отдельного разрешения.
- Не запускай платные эксперименты без отдельного разрешения владельца.
- Не изменяй существующие успешные результаты экспериментов.
- Не меняй архитектуру молча: каждое существенное решение обосновывай тестами.

## Что нужно предоставить по итогам

1. Описание первопричины пропусков.
2. Список изменённых компонентов.
3. Схему новой агентной логики.
4. Тесты, подтверждающие universal LLM fallback.
5. Объяснение новой политики Validator.
6. Результаты регрессий.
7. Результаты benchmark и расход токенов — если live-прогон был разрешён.
8. Матрицу готовности блока B.
9. Аудит и план поддержки Coding.
10. Список оставшихся рисков и следующего приоритета.

## Критерий успеха

Нельзя считать задачу выполненной только потому, что агент снова получил высокий процент на исходном наборе.

Главный критерий:

**Новая, ранее неизвестная задача должна получать полноценную попытку решения моделью и инструментами, а не автоматически отбрасываться ограниченным локальным анализатором.**

Сохрани бюджет и безопасность, но перестань использовать отсутствие заранее реализованного строгого Validator как запрет на работу LLM.

Начни с аудита реального кода и минимального воспроизведения отказов, затем устрани первопричину. Не занимайся Coding до того, как основной агентный цикл станет работоспособным.
