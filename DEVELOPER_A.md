# Разработчик A: управление ресурсами, оркестрация и запуск

## Твоя цель и текущая точка

Сделать harness, который распределяет ограниченный бюджет между задачами,
контролируемо вызывает модели через openJiuwen и успевает сохранить результаты.
Ошибки твоего направления могут потерять весь конкурсный результат: перерасход,
незаписанный ответ, несовместимый запуск или неудачная сборка.

Общие определения A1 и C01 реализованы; SDK 0.1.19 проверен на Windows/Python 3.11,
Linux-проверка остаётся открытой. Подробности — [отчёт A1](docs/a1-report.md).
Ledger A2 и его локальные проверки реализованы, см. [отчёт A2](docs/a2-report.md).
LLM Gateway A3 реализован с mock HTTP-проверками; реальные профили/caps ещё не подтверждены,
см. [отчёт A3](docs/a3-report.md). Загрузчик и baseline-планировщик A4 реализованы,
см. [отчёт A4](docs/a4-report.md). A5-lite связывает реальный SDK workflow,
проверку и текстовую публикацию: [отчёт A5-lite](docs/a5-report.md).
Production B-minimal и Docker baseline A6 подготовлены: [отчёт A6](docs/a6-report.md).
Полное A5 с публикацией исходных изменений и Linux/контейнерная проверка ещё предстоят.
Этот файл не является разрешением
автоматически запускать API или публиковать репозиторий.

## Твои каталоги и граница с B

Ты владеешь `src/nsu_budget_agent/{task_io,planning,budget,llm,orchestration,
submission,telemetry}/`, `configs/`, будущими корневыми `run_agent.py`, `Dockerfile`
и фиксацией зависимостей. `contracts/` и `docs/contracts.md` меняются совместно;
ты собираешь согласованный вариант, B проверяет потребителей.

B владеет `tools/`, `solvers/`, `validation/`, `evaluation/`, тестовыми данными
и качеством решений. Не реализуй за него второй набор инструментов или решателей.
Не помещай специфичные правила CSV, арифметики или исправления Python в планировщик.

## Contracts v1: решения уже приняты

Источник истины — [Contracts v1](docs/contracts.md). Технический этап S0 закрыт
спецификацией: поля, ошибки, async-границы и политика принятия больше не требуют
повторного проектирования. Твоя первая задача — перенести их в минимальные общие
Python-определения без изменения смысла. B использует те же определения.

| Что реализуешь | Контракт и результат |
| --- | --- |
| Загрузка/адаптер | async `load(Path) -> LoadReport`, `load_task(Path) -> TaskSpec`; безопасные artifacts, исходные корни и protected-тесты |
| Реестр | sync `register`, `all_solvers`, `get`; ровно один generic, регистрация только до запуска |
| Планировщик | sync `choose(...) -> PlanDecision или None`; TaskProgress, общий BudgetSnapshot, профиль RunConfig |
| Бюджет | sync `open_attempt/reserve/mark_dispatched/release_unsent/record_usage/snapshot/close_attempt/halt`; один event loop |
| Шлюз | `bind(attempt_id, step_index, budget) -> LLMSession`; async `complete(LLMRequest) -> LLMReply`, один запрос на шаг |
| Оркестрация | async `run_attempt(...) -> AttemptResult`; единственный цикл в JiuwenAdapter |
| Принятие | sync `decide(AttemptResult, ValidationResult) -> AcceptanceDecision` по точному правилу v1 |
| Публикация | `plan(TaskSpec) -> PublicationPlan`; async `publish(...) -> SubmissionReceipt` |

Все DTO — frozen/slots/kw_only dataclasses из stdlib, порты — Protocol. Единица
бюджета — целая десятая конкурсного токена. `None` обозначает неизвестность.
SDK-цель — openJiuwen 0.1.19, Python 3.11; проверка и импорт API только в
`orchestration/`. Нельзя переносить типы SDK в интерфейсы B.

От B получаешь stateless `Solver.assess/step`, ToolExecutor.catalog/execute и
Validator.validate. Решатель возвращает ToolCall, CandidateAnswer или StopAttempt;
**AttemptResult создаёшь ты**, а не B. После кандидата ты замораживаешь staging,
строишь diff/snapshot, передаёшь его на validate и применяешь решение о публикации.
Для inconclusive принятие разрешено только при passed всех blocking-проверок
и отсутствии failed. Сохранённый результат не объявляется засчитанным жюри.

Начальный сценарий уже выбран: неизвестная метка типа, текстовый файл с новым
именем, одно чтение инструментом и строковый ответ; LLM-double и реальный
JiuwenAdapter. Вариант без workspace обязателен. Живой API для него не нужен.

## Последовательность и задачи

### A1. Перенести Contracts v1 в общие определения — P0

- **Назначение:** дать B общий импорт без нового обсуждения форматов.
- **Результат/пути:** `contracts/models.py`, `contracts/ports.py`, проверки C01;
  отдельный маленький PR со всеми DTO/Protocol v1. SolverContext находится в ports.py
  рядом с LLMSession, остальные DTO — в models.py; обратного импорта models → ports нет.
  Никаких реализаций сервисов в contracts.
- **Зависимости:** спецификация v1 уже завершена; готовность кода B не требуется.
- **Работа:** перенести типы, defaults, валидацию и сигнатуры буквально по смыслу.
  Далее проверить интеграцию SDK 0.1.19 на Python 3.11; несовместимости локализовать
  в JiuwenAdapter. Фиксация зависимостей не должна задерживать ранний PR с stdlib-контрактами.
- **Приёмка:** [ ] импорт общих определений без сети и SDK; [ ] нет двух определений
  одного DTO; [ ] unknown/None, bool-vs-int, пути и состояния покрыты C01;
  [ ] B может подключить ToolExecutor/Solver/Validator по существующим Protocol;
  [ ] отдельная проверка выбранного SDK и воспроизводимой установки описана честно.

### A2. Реализовать книгу бюджета — P0, надёжность P1

- **Назначение:** управлять общим лимитом при последовательных и параллельных вызовах.
- **Результат/пути:** `budget/`, `tests/unit/`, `tests/contracts/`.
- **Зависимости:** A1; подтверждение Q1 нужно для окончательной семантики прокси,
  но локальный учёт можно разрабатывать на согласованных тестовых сценариях.
- **Работа:** резервировать вход и максимальный выход до запроса; учесть активные
  резервы, лимит попытки и глобальный остаток; списывать usage один раз; представить
  неизвестный расход после таймаута. Использовать целые десятые бюджетной единицы.
- **Приёмка:** [ ] параллельные запросы не получают один и тот же остаток;
  [ ] повторная доставка usage не списывает дважды; [ ] reasoning учитывается ровно
  один раз; [ ] потерянный ответ не освобождает резерв как бесплатный запрос;
  [ ] отказ до отправки и ошибка после отправки различаются;
  [ ] новые запросы прекращаются при лимите, готовые результаты сохраняются.

### A3. Создать единственный LLM-шлюз — P0, ошибки P1

- **Назначение:** изолировать транспорт и различия провайдера от решателей.
- **Результат/пути:** `llm/`, события `telemetry/`, сетевые doubles в `tests/`.
- **Зависимости:** A1/A2; текстовый LLMRequest/LLMReply и протокол действий уже заданы v1.
- **Работа:** адрес/ключ из окружения, allowlist четырёх моделей; нормализация usage;
  таймаут и отмена. В v1 один complete — одна отправка; все автоповторы SDK/framework
  отключены. Новую попытку разрешает планировщик, она имеет новый ID/лимит.
  Native tools/JSON mode не нужны: шлюз возвращает текст. Проверить ProviderProfile
  и границы полного выхода; в strict не отправлять запрос при непроверенных лимитах.
- **Приёмка:** [ ] каждый запрос получает lease; [ ] секреты не попадают в события;
  [ ] проверены success, malformed response, временный rate limit, окончательный
  лимит, timeout и отсутствие usage; [ ] лимит reasoning не выдан за проверенный,
  если семантика неизвестна; [ ] обычные тесты не обращаются в сеть.
- **Реальная проверка:** только отдельный небольшой smoke в рамках разрешённой
  последующей реализации; зафиксировать модель, расход и наблюдаемую семантику.

### A4. Загрузка и минимальный планировщик — P0

- **Назначение:** принимать весь набор и выбирать применимый способ решения.
- **Результат/пути:** `task_io/`, `planning/`, контрактные и модульные тесты.
- **Зависимости:** A1; SolverOffer и порты уже заданы в v1, для разработки достаточно тестового Solver без ожидания B2.
- **Работа:** адаптер манифеста организаторов, отдельные `task_root/work_root`,
  безопасный ввод без эталонов; явный список решателей, выбор по награде, оценкам
  и доступным ресурсам. Неподдерживаемый формат — диагностируемый результат.
  Общий решатель должен оставаться кандидатом без знакомой метки типа.
- **Приёмка:** [ ] новые имена файлов и отсутствие `workspace/` обработаны;
  [ ] новый решатель добавляется регистрацией без правки алгоритма очереди;
  [ ] неизвестная оценка не трактуется как нулевая стоимость;
  [ ] результат `unsupported` одного решателя допускает другой маршрут;
  [ ] в режиме отбора низкая награда не исключает одну из двух задач.

### A5. Исполнение через openJiuwen и публикация — P0, остановка P1

- **Назначение:** связать планировщик, инструменты B и сохранение в сквозной процесс.
- **Результат/пути:** `orchestration/`, `submission/`, `telemetry/`, integration tests.
- **Зависимости:** A2–A4, B1/B2; B4 задаёт результат локальной валидации. Место ответа
  и `OUT` изолировать до ответа Q2, а не размазывать предположение по решателям.
- **Работа:** workflow выполняет ограниченные шаги, собирает результат проверки,
  применяет политику v1 и сразу публикует. Ты владеешь staging, diff и snapshot;
  B исполняет один шаг и возвращает результат валидации, не второй цикл. Разделять статусы
  кандидата, локальной проверки и сохранённого ответа. Исходники публикуются раньше answer.txt; первая принятая сдача окончательная,
  повтор той же публикации идемпотентен. Многофайловая операция не объявляется
  атомарной транзакцией. Не требовать LLM-вызова только ради записи значения.
- **Приёмка:** [ ] реальный openJiuwen участвует в исполнении; [ ] ответ записан
  атомарно; [ ] исключение в другой задаче не уничтожает готовый результат;
  [ ] отмена/исчерпание бюджета прекращает новые вызовы; [ ] локальные тесты не
  объявляются доказательством скрытой корректности; [ ] разнородные маршруты используют
  один механизм публикации; [ ] тесты организаторов не меняются.

## Как работать независимо и интегрироваться

Порядок: Contracts v1 → короткий PR A1 → A2 → A3; A4 можно делать параллельно с A2/A3 после A1.
A5 интегрируется по мере готовности B1/B2; A6 начинается с минимального реального
сценария и завершается после B6. A7 не блокирует сдачу.

Передай B ранний PR A1, LLMSession-double с той же сигнатурой и ToolContext
со staging-корнем/лимитами. Не требуй от B деталей SDK, конфигурации прокси или ledger.
Для интеграции B передаёт assess/step, каталог схем и validate. Проверки C01–C12
из v1 распределяются по владельцам; общий сценарий C12 собираешь ты. Doubles находятся только в `tests/`; они не становятся
фиктивным runtime. От B принимай маленькие законченные инструменты/маршруты с
контрактными тестами. Ежедневный интеграционный PR предпочтительнее позднего слияния.

## Регламент, о котором отвечаешь прежде всего ты

Общий расход — вход/10 + выход, reasoning один раз; четыре разрешённые Qwen;
только выданный прокси. Локальные нейросетевые модели запрещены. До 5 сессий,
без GPU, 16 ГБ RAM, 1 час. CPU противоречивы: временно принимать 4. Runtime не
скачивает зависимости. Ответ сохраняется после каждой задачи, а не в конце.
Отбор — обе задачи. Бюджет, `OUT`, путь ответа и коды отказа пока уточняются;
не создавать фиктивный контракт организаторов. Доступ API до 20 ноября не
подтверждает дедлайн сдачи.

## Git и критерий передачи

Начинай от обновлённой `main`: `git switch main`, `git pull --ff-only`,
`git switch -c feature/a-budget-ledger`. Для следующей задачи — отдельная короткая
ветка. PR в `main`, reviewer B, описание поведения, контрактов и выполненных проверок.
Для последующего изменения v1 создай отдельный контрактный PR с B-review; не переписывай
общую историю и не делай force push в `main`. Синхронизация рабочей ветки:
сохранить работу коммитом, `git fetch origin`, `git merge origin/main`, проверить.
Первичная публикация описана в `docs/collaboration.md`; автоматической публикации нет.

Не коммить `.env`, ключи, локальные задачи, окружения, регистрации или сырые логи.
Для каждого этапа в PR укажи версию кода, команды реальных проверок и ограничения.
Изменение одних документов не требует запуска API.
