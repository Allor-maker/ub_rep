# B-minimal — первые автономные production-решатели

Реализовано в `feature/b-minimal`. Используются DTO/Protocol Contracts v1,
Ledger A2, Planner A4 и настоящий openJiuwen Workflow A5. NeuralDeep, сетевые
API, subprocess и task-код не вызываются. Новых зависимостей нет. Commit/push/merge
не выполнялись. LLM fallback, coding publication, adaptive scheduler и Docker не добавлены.

## Production-компоненты

- `tools/local.py`: LocalToolExecutor с read-only инструментами:
  `read_file`, `local_math`, `query_csv`, `audit_csv`, `lookup_markdown`. Чтение — только
  разрешённые source_artifacts внутри staging, с повторными no-follow открытиями
  A4, сверкой размеров/SHA-256 и запретом traversal, symlink/reparse/hardlink.
  Поддерживаются UTF-8/BOM текст, Markdown и CSV. expected/gold/manifest/answer
  недоступны даже при явно подложенном пути в ToolCall.
- `tools/calculations.py`: ограниченный интерпретатор AST, точная арифметика
  Fraction, строгий csv.reader и парсер Markdown-профилей. Нет eval/exec,
  произвольных функций, импортов, shell, выполнения Python из задания или сети.
  Decimal-контекст вызывающего кода не влияет на расчёт. Десятичные лексемы
  преобразуются прямо из исходного текста, без вычислений через binary float.
- `solvers/plans.py`: небольшая полностью проверяемая грамматика инструкций.
  Неиспользованный смысловой текст отвергается. Имена файлов, сущностей, товаров,
  числа и параметры извлекаются из задания/ArtifactRef, не из ID задачи или
  фиксированных ответов. Допустимый служебный текст о вычислении/выводе не исполняется.
- `solvers/deterministic.py`: stateless-решатели `local_math`, `local_search`,
  `local_data_analysis`. assess без I/O предлагает только применимый инструмент
  с нулевой LLM-стоимостью; вероятность успеха и время не выдумываются. Первый
  step возвращает ToolCall; следующий проверяет историю и возвращает CandidateAnswer
  с evidence. Ошибка/усечение/недостаток фактов приводит к StopAttempt.
  Обязательный `generic` зарегистрирован как честный отказ для неподдержанного
  задания; общего LLM-решателя в B-minimal нет.
- `validation/local.py`: LocalValidator проверяет четыре обязательных blocking
  проверки: format, paths/evidence/пустой diff, protected_files по исходным хешам,
  snapshot по Contracts v1. Затем повторно строит план и вычисляет ответ инструментом
  по проверочной копии A5. Точный текст и необходимые evidence должны совпасть.
  Непустой неверный ответ отвергается. Неизвестный check_hint не превращается в
  exact_int; неподдержанное задание/неполная семантика блокируют сдачу. Для unittest
  возвращается blocking inconclusive visible_tests: код и тесты не исполняются.
  Для CSV дополнительно выполняется blocking `csv_independent`: независимая от
  вычислительного ядра решателя реализация `validation/csv_audit.py` повторно читает
  разрешённый staging через `audit_csv`, проверяет полноту фильтров и отдельно
  считает уникальные заказы либо строки. В ответ инструмента возвращается только
  результат аудита, а не весь CSV, поэтому max_output_bytes не ограничивает размер
  исходного CSV сверх лимита чтения. Идентичность вызовов и дедлайн проверяются.
- `solvers/composition.py`: production `build(ledger, config) -> Components` для
  существующего A5. Все зарегистрированные маршруты deterministic. DisabledLLMGateway
  — реальная недоступность способности: complete всегда возвращает unsupported,
  не имитирует ответ провайдера и не резервирует/списывает средства. Нет зависимости
  от tests или fake-компонентов. Учёт/состояния/публикация по-прежнему принадлежат A.

## Поддерживаемый охват

1. `Compute/Calculate/Evaluate <expression>.`: `+ - * / // % **`, скобки,
   целые и ограниченные десятичные числа. Степень 0–12, до 128 AST nodes,
   глубина до 16, выражение до 1024 символов, дроби/целые до 512 бит. Неограниченные
   степени, функции и код запрещены. Результат — целое или конечная десятичная
   дробь до 40 знаков; для 1/3 без заданного формата есть отказ, а не округление.
2. Последовательные складские операции: начальный запас, отгрузка по дням/партиям,
   поступления, брак, удвоение, деление с округлением вниз и добавление остатка.
   Выполняются только явно распознанные операции в исходном порядке. Неизвестная
   операция, отсутствующее число или отрицательный физический запас дают отказ.
3. CSV: сумма units, число orders, сумма units*price с явно заданным product,
   region и включительными границами month; проверяется заявленная схема и число
   строк. Дополнительно поддерживается запрос
   `In <file.csv>, what is the sum of <column> where <column> equals '<value>'?`
   с другими именами столбцов. Порядок столбцов, quoted cells, BOM и blank records
   поддерживаются. Повторы заголовков, неполные строки, некорректные числа,
   неизвестная агрегация/условие и отсутствующая tax-информация не угадываются.
   Orders — число различных непустых `order_id`, только если этот столбец явно
   объявлен в схеме задания и присутствует в заголовке. Повтор ID считается один раз.
   Пустые/пробельные ID, ID с окружающими пробелами, различающиеся только регистром
   ID и противоречивые регионы одного заказа дают отказ. Пустое/пробельное значение
   любого обязательного поля фильтра в любой строке считается недостатком данных,
   а не несовпадением. Это консервативное правило применяется ко всем агрегациям.
   Отдельное `count_rows` (совместимый alias `count`) считает именно записи; пример
   поддерживаемого вопроса: `In <file.csv>, how many rows where <column> equals '<value>'?`.
4. Markdown-профили: `# <entity>` и явные строки `Attribute: Value`. Поддержаны
   Born; Employer → Headquarters/Founded; Mentor → Born. Файлы выбираются по
   формату и заданной области каталога, сущность — по заголовку, не имени файла.
   Конфликтующие сущности/поля, отсутствующие связи и неструктурированный текст
   приводят к отказу. Не поддерживаются произвольные Markdown-статьи, внешние ссылки,
   скрытые факты, поиск в сети и свободные вопросы.

Пределы инструмента: суммарно min(max_read_bytes, 8 MiB) данных на вызов,
max_output_bytes без частично обрезанного ответа, до 256 Markdown-профилей,
до 100000 CSV records и 128 колонок, до 16 фильтров. Дедлайн проверяется при
чтении и вычислениях. Урезанное содержимое не используется как полное.

## Минимальные изменения A и запуск

1. В CLI default --components теперь `nsu_budget_agent.solvers.composition:build`.
   Это необходимо для самостоятельного production-запуска без выбора fake/factory
   оператором. Существующий явный --components остаётся доверенной настройкой;
   тест A5 на отсутствие компонентов заменён проверкой недоступного явного модуля.
   Core Engine/Planner/Ledger/Gateway/Publisher и публичные контракты не менялись.
2. В общем исключении служебных файлов A4 отсекаются `expected`/`gold` и варианты
   с разделителем или цифрой после слова, включая `.`, `_`, `-`, пробел и Unicode
   пунктуацию, без учёта регистра. Правило применяется к файлам и каталогам на
   всех уровнях discovery, загрузки, staging и вызовов инструментов. Например,
   `gold-standard.md`, `expected-answer.txt` и каталог `gold-hidden/` исключаются;
   обычное имя `golden.txt` не исключается. Без этого Loader мог бы прочитать gold
   ещё до staging/B. **Эталоны с произвольными именами такая эвристика не защищает:**
   организатор/оценщик должен физически отделять gold от входного дерева агента.
   Значения expected/gold внутри task.json не извлекаются: Loader использует
   прежний allowlist публичных полей. Raw manifest не передаётся B.
3. CI добавляет ветку B, Mypy новых компонентов и Protocol consumers. Полный
   unittest discovery включает новые тесты; SDK smoke сохранён. Windows lock
   для Linux не используется.

```powershell
$env:BUDGET = '0'
python run_agent.py --tasks-dir <fresh-task-copy> --budget-unit units_x10
```

Ключи LLM_BASE_URL/LLM_API_KEY не нужны, HTTP transport не создаётся. В ограниченной
Windows-среде используйте `--staging-dir <existing-private-temp-parent>` вне каталога
задач. Нужны уже используемые Python 3.11 и SDK 0.1.19. Strict-mode A3 не выключен;
изменений verified-профилей нет. Даже при положительном BUDGET все маршруты
B-minimal имеют нулевые LLM calls и cost.

**Единицы BUDGET остаются неподтверждёнными.** Поэтому --budget-unit обязателен,
команда только `python /app/run_agent.py --tasks-dir /data/tasks` ещё требует
согласованной конфигурации единицы в A6. Без этого запуск честно отказывает,
а не выбирает масштаб молча. Нулевой BUDGET в тестах — действительное значение,
достаточное для deterministic-маршрутов.

## Измеренные результаты

Все прогоны использовали production factory и реальный workflow openJiuwen.
Исходные каталоги не изменялись: тесты через Loader экспортировали только публичные
поля и разрешённые artifacts в свежие временные копии, без raw manifest, gold,
expected или старых answer.txt. Ответы проверялись отдельными формулами/CSV-агрегациями
и поиском явных публичных фактов в тестовом оценщике. Никакой gold не читался.

| Набор | Проверенных правильных answer.txt | Остальные без answer.txt | LLM calls |
| --- | ---: | ---: | ---: |
| Исходные локальные примеры, 8 задач | 6 / 8: 2 math, 2 search, 2 data_analysis | 2 coding | 0 |
| Локальный smoke benchmark, 12 задач | 6 / 12: по 2 на поддержанный тип | 3 coding, 3 без достаточного поддержанного условия | 0 |
| Локальный synthetic benchmark, 100 задач | 60 / 100: по 20 на math/search/data_analysis | 25 coding и 15 с отсутствующими данными/неподдержанным вопросом | 0 |
| Переносимый собственный сквозной набор, 6 задач | 3 / 6: math, CSV, Markdown | отсутствующий факт, неизвестная операция, coding | 0 |

Smoke пересекается с полным benchmark; результаты не складываются. Это проверка
корректности по публичному условию, не официальный балл жюри/скрытых тестов и не
оценка обобщения на произвольные естественные формулировки. Ни ID задач, ни строки
правильных ответов этих наборов не присутствуют в runtime-решателях.
После исправления review повторный прогон не изменил результат: **60/100**, smoke
**6/12**, исходные примеры **6/8**. Тестовый оценщик считает разные order_id, а не
число строк, и не обращается к gold. Новые ручные синтетические случаи с повторными
ID ранее выдавали неправильный ответ, поэтому стабильный benchmark не доказывает
отсутствие такой ошибки в других данных.

## Проверки и воспроизведение

Добавлены 23 unit-теста и 7 integration-тестов, а также структурная проверка
Protocol в `tests/contracts/typecheck_b_minimal.py`. Тесты содержат собственные
малые данные с ручными ожидаемыми результатами и независимые публичные расчёты
для внешних наборов. Проверяются неверные непустые кандидаты, evidence, protected,
неизвестные hints, malformed CSV, дубли сущностей, новые имена/колонки, отсутствие
оценок вероятности, лимиты, AST code injection, symlink/traversal, stateless history,
Decimal-контекст, default CLI без ключей/fake и отсутствие открытия expected/gold.
Регрессии после review включают файлы и вложенные каталоги с разными именами
эталонов, повтор order_id, отдельный count rows, неоднозначные ID/регионы,
пустые фильтры во всех агрегациях и проверку кандидатов против ручных оракулов.
Специальный тест подменяет результат query_csv старым ошибочным числом строк:
semantics проходит, но `csv_independent` отклоняет кандидат. Аналогично проверен
ложный ноль при пустом фильтре; различающиеся call_id не принимаются. Есть проверка
корректной работы аудита, когда CSV больше max_output_bytes, но укладывается в
max_read_bytes. Только небольшие данные аудита выходят из инструмента.

```powershell
$env:PYTHONPATH = 'src'
$env:MYPYPATH = 'src'
```

Windows/Python 3.11: **204 tests, OK (skipped=6)**: 198 выполнены, прежние 5
пропусков A4 и 1 новый symlink-тест из-за Windows privilege 1314. Ruff lint и
format-check проходят; Mypy — без ошибок в 45 файлах, выполнена команда из CI YAML.
Три теста локальных наборов выполнены здесь; если внешние каталоги отсутствуют,
они явно пропускаются. В Linux CI переносимые production-тесты и CLI остаются
обязательными, внешние/private наборы в репозиторий не копируются. YAML проверен.
Результат GitHub Actions/Linux не подтверждён; Docker не запускался.

## Ограничения и остаточные риски

- Это узкие распознаваемые задачи, не свободное рассуждение на английском/русском.
  Перефразировка, многошаговый поиск вне перечисленных отношений, новые агрегации,
  иной CSV dialect/кодировка и неструктурированный Markdown обычно дают отказ.
  Для числа orders/rows и полноты фильтров есть отдельный CSV-аудит, не вызывающий
  общее вычислительное ядро. Грамматика плана, стандартный CSV-парсер и часть
  проверки остальных агрегаций остаются общими: их общая ошибка возможна.
  Отдельные тестовые вычисления не являются универсальным семантическим оракулом.
- «Отказ» означает недостаток поддержанной информации/возможности, а не доказательство
  математической невыполнимости задачи. Значение из Markdown доказывается только
  содержимым источника, не независимым фактом внешнего мира.
- Произвольный код, shell и тестовые процессы недоступны; ToolLimits памяти/числа
  процессов не превращаются в ОС-песочницу. Вместо этого исполняются только
  ограниченные доверенные алгоритмы. Зависший filesystem I/O может задержать
  cancellation до завершения joined worker — прежняя граница A5.
- Production-маршрут не использует fake. Оператор всё ещё может явно выбрать
  произвольную доверенную --components factory; упаковка production должна
  исключать tests и не брать конфигурацию из задач. Недоверенные Python-плагины
  не изолированы этим механизмом.
- Нужна Linux/контейнерная проверка зависимостей, tmpfs/read-only корня и hard-link
  publication. Сохраняются остаточная гонка внешнего писателя и ограничения
  answer-only A5; coding-изменения никогда не публикуются.
- Будущие LLM/coding/новые читатели подключаются отдельными согласованными
  реализациями текущих Protocol; B-minimal не ослабляет strict A3 и не создаёт
  параллельный бюджет или самостоятельный цикл исполнения.
