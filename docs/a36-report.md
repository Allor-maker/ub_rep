# A3.6 — LLM-to-Tools fallback для search и data_analysis

Ветка `feature/a36-llm-tools`. Реальных вызовов NeuralDeep нет. Contracts v1,
формула бюджета, A2, A3 и A5 не изменены. Базовая offline composition и существующие
deterministic solvers сохранены; новая возможность включается только существующей
opt-in factory `nsu_budget_agent.solvers.composition:build_with_llm`.

## Исполнение и границы плана

`solvers/llm.py` сначала проверяет наличие поддерживаемого semantic verifier и
read-only инструментов. Для data-задачи step 0 выполняет ровно один complete
через привязанный LLMSession A3. В prompt находятся инструкция и ограниченный
список разрешённых путей; содержимое Markdown/CSV, ответы и эталоны не передаются.
JSON использует форму Contracts v1:

```json
{"kind":"tool","tool_name":"query_csv","arguments":{"path":"ledger.csv","aggregate":"sum","columns":["amount"],"filters":[{"column":"region","op":"eq","value":"west"}]}}
```

Разрешён один query_csv (sum, count_rows, product_sum, один точный equality-фильтр)
или lookup_markdown (явная сущность, поле, максимум одна связь Employer). Нет
read_file как действия модели, произвольного кода, shell, eval, SQL, внешнего
поиска или динамических плагинов. Модель не возвращает итоговые числа. Максимум
выхода JSON-плана 192 токена; A3.5 числовой маршрут сохраняет прежний cap 96.
В strict границы полного выхода и входа по-прежнему предоставляет подтверждённый
адаптер, а не эта константа или результаты smoke.

`validation/data_plan.py` независимо от модели полностью разбирает инструкцию
и связывает JSON-план с её поддерживаемой семантикой. Операция, колонки, literal
фильтра, сущность, цепочка и пути должны точно соответствовать инструкции;
неизвестные ключи, дубликаты JSON-ключей, другая агрегация и лишние действия
отвергаются до исполнения. Отсутствие такого разбора означает отказ до LLM.
Имеются шесть семейств явных формулировок (примеры в fixtures); неизвестные
модификаторы, неоднозначные requests и неподтверждённые подразумеваемые схемы не
игнорируются. Этот закрытый verifier не обещает понимание произвольного языка.

План возвращается как ToolCall существующему JiuwenAdapter. Настоящий openJiuwen
исполняет production LocalToolExecutor, сохраняет StepRecord; на step 1 stateless
решатель проверяет историю и строит CandidateAnswer из локального результата.
Второго LLM-запроса, исправляющего цикла или скрытых retries нет. При ошибке
инструмента/плана, length/other, unknown usage или недоступном бюджете — отказ.
Нужно минимум два разрешённых шага. Пара задача/generic после отказа по evidence
не повторяется A5 без новых данных, как реализовано в A3.5.

## Независимая проверка

FallbackValidator сохраняет blocking-проверки формата, исходных/protected файлов,
manifest, evidence и snapshot B-minimal. Для data-кандидата он заново связывает
инструкцию с разрешённой операцией и читает файлы через production read_file
из validation-копии staging. Проверяются имена инструментов/call_id, статус,
отсутствие усечения, allowlist файлов и суммарный лимит чтения. Пути с excluded
expected/gold именами запрещены также semantic verifier; I/O по-прежнему защищено
существующими A4/B средствами от traversal и symlink/hardlink escape.

Числа CSV пересчитываются отдельным кодом: Decimal с собственным context и
DictReader вместо Fraction/reader ядра исполнения. Неполные строки, дубликаты
колонок, отсутствующие обязательные значения фильтра (даже в отфильтрованных
строках), невалидные числа и лишние ячейки отвергаются. Считаются **records/rows**,
а не заказы. Сумма и сумма произведений точные, неявного округления нет.

Markdown проверяется отдельным parser/lookup: одна явная сущность в заголовке,
уникальные свойства, точные связи/поля, существующие сущности цепочки, формат
года/email. `directory/*.md` означает непосредственные дочерние Markdown-файлы,
не рекурсивный и не глобальный поиск. Повторные сущности/свойства и неструктурный
текст приводят к отказу. Текст свойств остаётся данными и не становится инструкцией.
Это не доказывает истинность произвольно отравленных исходных фактов во внешнем
мире; произвольно названные gold должны быть физически отделены от input.

Успешного ToolResult недостаточно: тестовый инструмент, подменяющий ответ на
`999` при правильном плане, не проходит независимую валидацию CSV и Markdown.
Валидатор не доверяет итоговым числам модели или отчёту исполнителя.

## Исправления после review A3.6

- **Согласованная подмена ToolResult.** Текст `read_file` восстанавливается в
  допустимые исходные UTF-8 байты с BOM либо без него и сверяется по размеру и
  SHA-256 с `TaskSpec.artifacts`; поле хеша, присланное самим инструментом, не
  используется. Также проверяется совпадение метаданных разрешённого артефакта
  в ToolContext и TaskSpec. Регрессия: подмена результата суммы и read_file на
  согласованное `99` при неизменённом файле с ответом `19.75` отклонена, несмотря
  на одинаковый размер и переданный инструментом поддельный хеш; answer.txt нет.
  Проверены UTF-8 с BOM/без BOM, CRLF, не-ASCII текст и двойной BOM на уровне
  реконструкции. Недоступность проверки остаётся blocking inconclusive.
- **Неоднозначная search-сущность.** Незаключённое в кавычки имя проверяется
  консервативно: альтернативы/отрицания и ряд связок/условий, possessive и
  несоответствующие ограниченному синтаксису части не принимаются. `Alice or Bob`
  с тремя соответствующими профилями отвергается до LLM, стоимость 0. Тесты
  включают and/or/not/without/except, уточнение места и остаток после инструкции.
  Это синтаксический фильтр, не универсальное распознавание неоднозначности;
  некоторые корректные имена с частицами в нижнем регистре также будут отклонены.
- **Предварительная проверка размера.** До complete сопоставляются общий размер
  artifacts с лимитом manifest Validator и минимально возможный размер ответа
  read_file с лимитом вывода, с запасом на удаляемый UTF-8 BOM. Гарантированно
  невыполнимые случаи дают отказ без запроса; проверка не предсказывает весь
  размер JSON после экранирования и потому может пропускать пограничные случаи.
  Для файла **69 байт при max_read_bytes=20**: HTTP-запросов 0, spent=held=0,
  answer.txt не создан. Отдельно покрыты превышение из-за другого artifact,
  лимит вывода и допустимая граница равенства размера лимиту.

- B-minimal: **0/6**, нет answer.txt, LLM-расход 0.
- Opt-in A3.6 с реальными A2/A3 и MockTransport: **6/6**, прибавка **+6**;
  6 SDK workflow, 12 шагов, 6 HTTP-запросов, 3 CSV/3 Markdown tool action и
  7 независимых read_file. Совпадение каждого ответа проверяется внешним оракулом.
- Usage задан тестом: **720 prompt + 288 completion**, reasoning=0 (included).
  Списание **3600 внутренних Units** = 6×(120+10×48), held=0. Это mock-usage,
  **не измерения NeuralDeep**, токенизатора, качества модели или реальной экономии.
  Резерв каждого mock-запроса — 4096+10×192=6016 Units; bound 4096 подтверждён
  исключительно тестовым transport fixture и не пригоден для реального провайдера.

Негативные сквозные тесты: другая операция/колонка/цепочка, traversal/expected/gold,
неразрешённый tool, неоднозначный текст, несуществующая колонка, пустой фильтр,
prompt injection как свойство и как неструктурный текст, unknown usage и нехватка
бюджета. При unknown один запрос удерживает 6016 Units; инструменты и публикация
не запускаются. При бюджете 1000 запрос не отправляется, spent=held=0.

## Ограничения и production

Без подтверждённого compatibility adapter реальный production LLM по-прежнему
fail-closed. Нового trusted adapter, verified-флагов, best_effort для production
или прямого HTTP из Solver не добавлено. Обычный конкурсный CLI остаётся offline
B-minimal. Активация opt-in описана в [A3.5](a35-report.md).

Поддерживаемая семантика намеренно ограничена явными полями/фильтрами/отношениями.
Эти новые шаблоны также можно было бы позднее перенести в deterministic маршруты:
LLM здесь предлагает план под независимым guard, а не доказывает произвольное
понимание текста. Нет CSV joins, fuzzy matching, агрегации по неявной бизнес-схеме,
неоднозначного округления, CSV scalar selection, нескольких tool actions, coding
или A7. Prompt/model routing не калиброваны по реальному NeuralDeep.

Блокеры A3.5 сохраняются: авторитетные input/framing bounds, полный output cap
с reasoning, правила usage/биллинга, поздняя сверка unknown. Известное ограничение
некооперативного response.aclose после полного чтения может нарушить hard deadline;
оно не исправлено этим этапом и не скрыто успешными тестами.
