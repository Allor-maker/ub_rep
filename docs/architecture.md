# Архитектура: расширяемость без отдельной платформы плагинов

Статус: архитектура зафиксирована в [Contracts v1](contracts.md). Реализован общий
слой A1 и C01; сервисы ещё предстоят. Python 3.11, SDK-цель openJiuwen 0.1.19.
SDK smoke прошёл на Windows; Linux-проверка открыта, см. [отчёт A1](a1-report.md).

## Основной выбор

Один Python-проект, один контейнер, общий бюджетный контроллер. openJiuwen
исполняет процесс попытки, включая вызовы инструментов и переходы между шагами;
его использование не сводится к формальному импорту.

Планировщик выбирает задачу и решатель по награде, оценке успеха, затратам,
времени и применимости. Он не содержит ветвления по закрытому списку `math`,
`search`, `data_analysis`, `coding` и не знает о расположении `sales.csv` или `mylib.py`.

Поток: загрузчик → нормализованная задача → оценка применимости → попытка
решения → локальная проверка → публикация → обновление очереди.

## Три точки расширения

1. **Входной адаптер** переводит конкретный манифест в `TaskSpec` и описания
   артефактов. Первым станет формат организаторов. Корень задачи и `workspace/`
   различаются явно. Новый манифест не должен менять бюджет и планировщик.
2. **Инструмент/читатель данных** предоставляет ограниченное представление
   артефакта. Для неизвестного формата возвращает явную неподдерживаемость;
   бинарный файл не интерпретируется молча как текст. При необходимости позже
   добавляется новый читатель, а не универсальная система обработки всего.
3. **Решатель** чистой функцией assess сообщает применимость; async step возвращает
   один ToolCall, CandidateAnswer или StopAttempt. Он stateless и не исполняет
   инструменты сам. Единственный цикл, ограничения и AttemptResult принадлежат
   JiuwenAdapter A. Не более одного вызова LLMSession на шаг; собственных клиентов нет.

Начальная регистрация — обычный явный список в коде. Не нужны загрузка плагинов
из сети, сторонние entry points, динамические импорты из задания, отдельные
микросервисы или сложная иерархия классов. Регистрация нового решателя должна
требовать только его реализации, тестов и добавления в список.

## Неизвестность — штатный случай

- `task_type` — открытая необязательная подсказка. Неверный или отсутствующий тип
  не запрещает использование подходящего инструмента.
- Манифест и артефакты не обязаны повторять учебные имена и структуру файлов.
- Если применимость неизвестна, допускается ограниченное исследование структуры
  задачи; LLM-исследование учитывается в бюджете.
- Общий маршрут не обещает решить любую задачу. Он возвращает результат,
  конкретное препятствие либо ограниченный расход без успеха.
- Неподдерживаемый формат, исчерпанный лимит, ошибка инструмента и доказанная
  противоречивость требований — разные причины остановки.
- Специализация принимается только вместе с проверкой на новых формулировках
  и задачах за пределами восьми примеров.

## Управление ресурсами

Прогноз стоимости нужен для выбора попытки. Резерв перед каждым запросом нужен
для управления фактическими обязательствами. Все одновременные вызовы используют
одну книгу бюджета; SDK и framework не делают скрытых повторов.

Вход оплачивается полностью. Reasoning не суммируется повторно, если уже включён
в completion. Неизвестный расход после таймаута сохраняется как неопределённый,
а не обнуляется. Гарантия верхнего лимита зависит от подтверждённой семантики
прокси; процентный запас сам по себе такой гарантией не является.

Внутренний режим auto выбирает coverage для двух задач, иначе portfolio.
Официальный способ обозначения отбора ещё неизвестен; адаптер запуска может
передать явный режим без изменения планировщика. Все входы описаны в RunConfig v1.

## Границы доверия и проверки

`evaluation/` может видеть эталоны; runtime в `src/` не импортирует оценщик и не
читает эталоны. В инструменты передаётся контролируемое представление файлов,
а не сырой манифест с `expected`. Неизвестные поля не автоматически добавляются
в контекст модели. Содержимое задач — данные, оно не меняет правила бюджета,
разрешённые модели и доступ к ключу.

Решатель предлагает кандидата. A замораживает staging и строит diff/snapshot;
`validation/` проверяет эту версию без эталона. A принимает её только при отсутствии
failed и passed всех blocking-проверок; nonblocking inconclusive допустим.
`submission/` публикует исходники, затем answer.txt. Первая сдача окончательная;
повтор идемпотентен. Это не многофайловая атомарная транзакция и не гарантия скрытых тестов.

Инструменты контролируют пути, выход за рабочий каталог и symlink, размер чтения
и вывода, время и процессы. Запускаемый код не наследует ключ API. `cwd` и отдельный
процесс не считаются полноценной песочницей. Не следует обещать изоляцию произвольного
shell без отдельной проверки возможностей финального окружения. До подтверждённой
ОС-изоляции инструмент исполнения кода unavailable. Обычные файловые инструменты
работают с отдельной staging-копией без manifest/expected, оригиналы меняет только publisher.

Контракты — только stdlib, компоненты зависят от Protocol, SDK импортирует только
orchestration. Никаких framework-типов в решателях. Сеть/процессы/длительный I/O
асинхронны; assess/choose/decide и ledger синхронны. Детали отмены, неизвестного
расхода и публикации определены в contracts.md и не выбираются каждым модулем заново.

## Что откладываем

ML-предиктор, сложную оптимизацию портфеля, многоагентные обсуждения, векторное
хранилище, динамическую загрузку расширений и автоматическую оптимизацию промптов.
Их добавление требует измеренного выигрыша, а не только наличия механизма в SDK.
