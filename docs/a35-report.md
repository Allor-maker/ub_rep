# A3.5 — NeuralDeep compatibility и минимальный LLM fallback

Ветка `feature/a35-neuraldeep`. Реальные NeuralDeep-запросы в ходе реализации
не выполнялись. Ни один профиль реального провайдера не объявлен подтверждённым.
Contracts v1 и A2 Ledger не изменены; после review внесено ограниченное изменение
cleanup в A3 Gateway, описанное ниже.

## Диагностика провайдера

`python -m nsu_budget_agent.llm.provider_smoke` без `--live` возвращает код 2
до создания HTTP-транспорта. Для отправки также обязательны `LLM_BASE_URL`,
`LLM_API_KEY` и явный положительный `--budget-units` во внутренних Units A2.
Диагностика не использует бюджет задач из BUDGET неявно.

После отдельного разрешения пользователя предусмотрен исследовательский
`--best-effort-diagnostic` с обязательным `--input-bound-tokens`: это оценка
входа, **не доказанный bound**. Только этот отдельный модуль использует
best_effort A3; production factory отказывается от best_effort. Профили
диагностики остаются `unverified`, оба verified-флага остаются false. Весь
резерв сохраняется как unknown, даже если числа в usage выглядят правдоподобно.
Реальный расход может превысить оценку или недоказанный cap; локальный бюджет
диагностики не объявляется жёстким ограничением списаний на сервере.

Пример отдельного управляемого запуска из корня репозитория (ключ и URL уже
установлены оператором в окружении; не помещать ключ в команду, Git или отчёт):

```powershell
$env:PYTHONPATH = 'src'
# Две небольшие платные пробы одной модели. Не запускать как часть обычных тестов.
.\.venv-a1\Scripts\python.exe -m nsu_budget_agent.llm.provider_smoke --live --best-effort-diagnostic --budget-units 12000 --input-bound-tokens 1024 --model qwen3.6-35b-a3b-noreason
```

Без `--model` проверяются все четыре разрешённых Qwen: по одному запросу
с cap 8 и 64, максимум восемь запросов, последовательно, без retries/redirects.
Вторая проба просит длинный вывод, чтобы наблюдать ограничение генерации;
полученный текст не печатается. По умолчанию передаётся `max_tokens`, отдельно
можно исследовать `--output-token-parameter max_completion_tokens`. Интервал
A3 не менее секунды, timeout запроса 20 с, общий deadline 180 с, тело до 64 KiB.
При ошибке транспорта/HTTP, нарушении наблюдаемой границы, отсутствии/дефекте
usage серия прекращается. В диагностическом режиме продолжение после unknown
возможно только для следующей заранее объявленной пробы с корректными числовыми
usage-полями; каждый такой запрос получает новый резерв A2. Это не повтор запроса.

JSON содержит только allowlist модели, статус/finish, числовые счётчики, признаки
наличия usage/reasoning и локальный spent/held. Нет URL, ключа, заголовков, текста
ответа, reasoning или сырых HTTP-ошибок. Проверки `cap_consistent_if_included` и
`cap_consistent_if_separate` — наблюдения при двух гипотезах, не вывод о тарификации.
`completed_samples=true` означает выполнение выбранной серии, а не готовность
strict-провайдера. `profile_promoted` всегда false. В strict-диагностике требуется
подтверждённый адаптер; `--adapter trusted_package:factory` заменяет оценки.

## Ручные наблюдения NeuralDeep

Результаты ниже предоставлены пользователем: пробы выполнялись им вручную в
диагностическом best_effort, не в рамках текущих проверок агента. Во всех пробах
`usage_status=unknown`, `profile_promoted=false`.

| Модель | cap=8 | cap=64 |
| --- | --- | --- |
| `qwen3.6-35b-a3b-noreason` | HTTP 200, корректный короткий ответ, completion=2, finish=stop | HTTP 200, completion=64, finish=length |
| `qwen3.6-35b-a3b` | HTTP 200, пустой финальный ответ, reasoning-текст присутствует, finish=length | HTTP 200, пустой финальный ответ, reasoning-текст присутствует, finish=length |
| `qwen3.8-27b-noreason` | HTTP 200, корректный короткий ответ, completion=2, finish=stop | HTTP 200, completion=64, finish=length |
| `qwen3.8-27b` | HTTP 200, completion=8, nested_reasoning_tokens=8, пустой финальный ответ, finish=length | Не выполнялась: после cap=8 серия корректно остановлена, `completed_samples=false` |

Для `qwen3.6-35b-a3b-noreason` reasoning-текст не обнаружен; для
`qwen3.6-35b-a3b` отдельное значение reasoning_tokens отсутствовало. Для
`qwen3.8-27b-noreason` сообщено `nested_reasoning_tokens=0`.
Для `qwen3.8-27b` при cap=8 наблюдались `cap_consistent_if_included=true` и
`cap_consistent_if_separate=false`: обе трактовки оставались возможными, поэтому
продолжение остановлено. У reasoning-моделей малый cap может израсходоваться до
появления финального ответа; наличие reasoning-текста и счётчиков не устанавливает
правила тарификации. Указанные ответы и счётчики — отдельные наблюдения, а не
доказательство максимального входа, полного output cap или семантики reasoning.
Надёжный bound входа с framing, полный cap с reasoning и учёт оплаты по-прежнему
требуют авторитетного подтверждения для каждой модели и проверенного адаптера;
до этого production strict остаётся заблокирован для соответствующей модели.

## Подтверждённая совместимость и production

`llm/compatibility.py` определяет внутренний `ProviderCompatibility` с reviewed
функцией input_bound, профилями, выбранным именем output-параметра и ссылкой
`evidence` на гарантии/ревью. Конфигурация загружается только из явного доверенного
`LLM_COMPATIBILITY_ADAPTER=package:factory`, не из задачи, ответа модели или smoke.
Непустая evidence — ссылка для ревью, сама по себе не доказательство. Доверенный
Python-адаптер обладает полномочиями кода приложения и должен быть проверен.
Профили копируются в read-only mapping, значения — неизменяемые DTO A1.

Реального адаптера с доказанным bound в репозитории нет. До его появления следующий
запуск завершится безопасной ошибкой конфигурации **без отправки**:

```bash
python /app/run_agent.py --tasks-dir /data/tasks --components nsu_budget_agent.solvers.composition:build_with_llm
```

Когда адаптер подтверждён, оператор устанавливает LLM_BASE_URL, LLM_API_KEY,
LLM_COMPATIBILITY_ADAPTER и при необходимости LLM_MODEL. Все четыре модели
разрешены; default маршрута — `qwen3.6-35b-a3b-noreason` как выбор короткого
формата, а не измеренное доказательство дешевизны/качества. Production factory
требует strict и подтверждение всех трёх условий для выбранной модели: bound
входа, cap полного выхода и reasoning_mode. Наличие ключа само по себе ничего
не включает. Обычная команда конкурса продолжает использовать offline B-minimal.

## Минимальный generic Solver и валидация

`solvers/llm.py` реализует существующие assess/step. В registry сохраняется
ожидаемый ID `generic`; deterministic routes сохраняют приоритет и нулевые
LLM-возможности. Оценки стоимости, времени и вероятности generic остаются None.
В попытке не более одного complete, cap 96, только короткий JSON
`{"answer":"...","evidence_paths":[]}` либо отказ. Нет native tools, исполнения
сгенерированного кода, самостоятельного цикла, корректирующих вызовов или
внутренних retries. A5 управляет попытками; его существующий предел две попытки
на задачу не изменён. Неполный, length, malformed/duplicate JSON, неизвестный usage
или непредусмотренный evidence приводят к StopAttempt, без публикации.

Генератор не ограничен знакомым ID/типом задачи, но перед отправкой требует
доступный независимый semantic verifier. Сейчас он покрывает ровно два
полностью потребляемых формата инструкции:

- `What is the exact value of (2+3)*4? Return only the result.`
- `Solve for x: 3*x+2=14. Return only the value of x.`

`validation/llm.py` проверяет ответ отдельной точной Fraction/AST-арифметикой
и доказывает единственность линейного решения. Код модели не исполняется.
Нелинейные, неоднозначные, неполные инструкции, неизвестный формат проверки,
непредставимый конечной десятичной дробью ответ и coding отвергаются до LLM.
Сохранены blocking-проверки формата, manifest, protected files и snapshot из
production B; текст модели не объявляется evidence сам по себе. Новая композиция
использует тот же production ToolExecutor и Validator Protocol, ни один путь
не читает expected/gold. Артефакты модели пока не отправляются.

Это инфраструктурный минимальный fallback, а не общее решение произвольных
search/data/math задач. Указанные уравнения B-minimal ещё не поддерживает;
при этом verifier уже умеет вычислить их точный ответ. LLM на этом поднаборе
не обещает преимущество перед будущим детерминированным маршрутом. Для более
широкого покрытия нужны независимые проверки семантики/evidence; повторный
LLM-ответ или голосование моделей такими проверками не считаются.

Каждый HTTP идёт только через существующие A3/A2: резерв до dispatch, известный
usage списывается один раз, неизвестный после отправки удерживается. Unknown
кандидат не публикуется. Для закрытия принадлежащего run HTTP-транспорта A5
`AgentRunner.aclose` дополнен optional aclose gateway в finally; интерфейс
LLMGateway v1 не меняется. Настоящий openJiuwen по-прежнему исполняет workflow.

## Исправления после review A3.5

- Диагностическая серия прекращается, если хотя бы одна ещё возможная трактовка
  полного выхода нарушает cap. На mock-серии из восьми запланированных запросов
  с `completion_tokens = reasoning_tokens = cap` отправляется только первый;
  `completed_samples=false`, профиль не подтверждается, резерв 100 Units остаётся
  unknown. Это по-прежнему best-effort: сам первый запрос не имеет доказанного
  серверного ограничения расходов.
- A5 исключает из текущего запуска конкретную пару задача/generic после отказа
  по evidence, отклонения кандидата или ошибки провайдера с удержанным резервом.
  Повтор той же попытки не видит новых данных: staging и история у новой попытки
  независимы. Другие маршруты остаются кандидатами; в coverage первые попытки
  других задач по-прежнему предшествуют повторам. На реальных A2/A3 и mock HTTP
  неверный кандидат теперь вызывает один запрос и 140 Units вместо двух и 280;
  unknown/timeout/429/500 — один запрос и удержание 1088 Units вместо двух и 2176.
  При финальной проверке найден и исправлен дополнительный вариант: HTTP 200 с
  точным usage, но повреждённым `choices`, раньше повторялся без новых данных.
  Теперь `invalid_output` исключает тот же generic-маршрут: один запрос, списание
  140 Units один раз, held=0 и отсутствие публикации. Другие solver routes доступны.
- При timeout/отмене *во время чтения* A3 больше не запускает `response.aclose()`
  в текущей корутине и не создаёт фоновую задачу для него. Поэтому воспроизведённый
  случай с зависшим чтением и `aclose`, игнорирующим отмену, завершается; после
  отправки весь резерв остаётся unknown/held. Немедленное закрытие отдельного
  response при таком отказе не гарантируется: освобождение соединений остаётся
  обязанностью принадлежащего Gateway транспорта при его закрытии. Для произвольного
  стороннего транспорта даже это освобождение не гарантировано.

**Остаётся открытым:** `httpx.Response.aiter_raw()` сам вызывает асинхронный
`aclose()` после полного чтения тела. Если этот `aclose()` бесконечно подавляет
`CancelledError`, дедлайн не может принудительно завершить корутину: mock с
успешно прочитанным телом и таким закрытием оставался активным после timeout.
Аналогично произвольный код транспорта или его финального `aclose()` может не
кооперироваться. Без изменения модели исполнения (например, отдельного процесса)
нельзя одновременно принудительно прекратить такую произвольную корутину и не
оставить зависшую задачу; полного hard deadline для такого транспорта не заявляем.
Исходное воспроизведение review с прерванным чтением устранено, но общая гарантия
«AgentRunner никогда не зависает на игнорирующем отмену cleanup» ещё не выполнена.
При финальной проверке этот остаточный случай снова воспроизведён на MockTransport:
после полного чтения и timeout 0,03 с задача оставалась активной через 0,15 с,
удерживая 720 Units. Тестовый поток затем был явно освобождён; к NeuralDeep
проверка не обращалась.

После этих изменений на Windows/Python 3.11 полный unittest discovery завершился
**239 тестами, OK (skipped=6)**; Ruff lint/format и Mypy (50 source files) прошли.
Все HTTP-проверки использовали MockTransport, реальный NeuralDeep не вызывался.

Финальная проверка после исправления `invalid_output` на Windows/Python 3.11:
**240 тестов, OK (skipped=6)**; Ruff lint и format-check — PASS, Mypy по команде
CI — PASS (50 source files). Host smoke с BUDGET=0 на свежей публичной копии:
**6/12**, остальные ответы не созданы, потрачено и удержано 0, 12 SDK workflows.
Docker smoke — SKIP: Docker CLI отсутствует. Linux CI ещё не запускался; локальный
PASS не подтверждает его результат. Ручные данные пользователя о NeuralDeep
записаны выше, новых реальных вызовов агент не выполнял.

## Проверки и блокеры

Offline-тесты используют реальные Gateway/Ledger, MockTransport и профили,
подтверждённые только для mock. Проверяются четыре модели, оба output-параметра,
included/separate/unknown usage, cap violation, timeout, ошибки, отсутствие ключа
и opt-in, отказ от неверного кандидата, нехватка бюджета, несколько задач,
приоритет deterministic и resource cleanup. Тестовые числовые оракулы заданы
вручную. CI ветки A3.5 включает полный discovery, Ruff/Mypy и прежний Docker smoke;
ключи, live-флаги и реальные вызовы туда не добавлены.

Фактические локальные результаты (Windows / Python 3.11):

- До исправлений review: unittest discovery **233 теста, OK (skipped=6)** — 227 выполнены,
  6 платформенных пропусков; реальные NeuralDeep HTTP-запросы запрещены doubles.
- Ruff lint и format-check прошли (73 Python-файла форматированы).
- Mypy по полной команде `.github/workflows/a1-ci.yml` прошёл, 50 source files;
  assignments новых Solver и Validator к Protocol добавлены в consumers B.
- Host smoke на свежей публичной копии локального benchmark при BUDGET=0:
  **6/12**, для нерешённых задач answer.txt отсутствует, spent=held=0,
  12 настоящих openJiuwen workflows. Переносимые smoke-фикстуры: **3/6**,
  нерешённые без файла ответа. Исходный benchmark не менялся.
- `python tests/docker/smoke.py --mode docker` действительно вызван, но прерван
  до запуска контейнера: `FileNotFoundError / WinError 2`, `docker` не установлен
  (Podman также не найден). Docker/Linux сборка, размер образа и smoke остаются
  неподтверждёнными. Docker job CI сохранён, live-вызовов в нём нет.
- Агент не выполнял реальный NeuralDeep smoke; ручные наблюдения пользователя
  приведены выше. Все verified-профили и HTTP-ответы автоматических тестов
  относятся исключительно к MockTransport, реальные ключи не читались из файлов
  и не выводились.

Команды проверки из корня репозитория:

```powershell
$env:PYTHONPATH = 'src'
$env:MYPYPATH = 'src'
$env:PYTHONDONTWRITEBYTECODE = '1'
.\.venv-a1\Scripts\python.exe -m unittest discover -s tests -v
.\.venv-a1\Scripts\python.exe -m ruff check src tests run_agent.py
.\.venv-a1\Scripts\python.exe -m ruff format --check src tests run_agent.py
# Mypy: полная команда шага Mypy в .github/workflows/a1-ci.yml.
.\.venv-a1\Scripts\python.exe tests/docker/smoke.py --mode host
.\.venv-a1\Scripts\python.exe tests/docker/smoke.py --mode docker
```

Для реального NeuralDeep остаётся отдельно подтвердить:

1. Доступность/имена всех моделей, endpoint, TLS/auth и output-параметр.
2. Полноту prompt usage, tokenizer/framing/скрытый overhead и доказанную верхнюю
   границу входа для произвольного запроса выбранного формата.
3. Входит ли reasoning в completion, полноту биллинга и cap всего оплачиваемого
   выхода, включая скрытый reasoning. Маленький smoke этого не доказывает.
4. Error/quota/rate-limit семантику, отсутствие скрытых повторов прокси,
   продолжение/списание после timeout и способ сверки неопределённого расхода.

Секреты и результаты платного smoke не подменяют эти гарантии. Диагностический
best_effort не является разрешением для production best_effort. В ходе проверок
агента нет live-вызовов; coding publication, A7, commit, push и merge не выполнялись.
