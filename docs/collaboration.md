# Совместная работа и первая публикация на GitHub

Команды ниже выполняет команда самостоятельно. При подготовке основы не создаются
удалённый репозиторий, commit, push или приглашения. Имена пользователей неизвестны;
`OWNER`, `YOUR NAME`, `YOUR EMAIL` нужно заменить собственными значениями.

## Первая публикация

1. В VS Code откройте `C:\VSCode\openJiuwen\nsu-budget-agent`.
   Локальный Git и начальная ветка `main` подготовлены; повторный `git init` не нужен.
   Убедитесь, что корень правильный, а remote ещё не настроен:

   ```powershell
   Set-Location 'C:\VSCode\openJiuwen\nsu-budget-agent'
   git rev-parse --show-toplevel
   git status --short --branch
   git remote -v
   ```

2. Если Git ещё не знает автора, настройте его только для этого репозитория:

   ```powershell
   git config --local user.name "YOUR NAME"
   git config --local user.email "YOUR EMAIL"
   ```

3. Проверьте список файлов, затем создайте первый коммит:

   ```powershell
   git add .
   git diff --cached --stat
   git diff --cached --check
   git diff --cached
   git commit -m "chore: prepare repository structure and development guides"
   ```

   Перед commit проверьте отсутствие ключей, `.env`, локальных задач, логов,
   окружений и регистрационных материалов. Если случайно добавили файл до первого
   коммита, уберите его из индекса через `git rm --cached -- PATH`; файл на диске
   сохранится. Не используйте `git clean` или `reset --hard` для обычной синхронизации.

4. На GitHub создайте пустой репозиторий `nsu-budget-agent` у выбранного владельца.
   Видимость выбирает команда. Не добавляйте на сайте README, `.gitignore` или
   лицензию: локальная история должна стать исходной. Авторизуйтесь через Git
   Credential Manager или SSH; не вставляйте токен в URL или документацию.

5. После создания пустого remote выполните первый push:

   ```powershell
   git remote add origin https://github.com/OWNER/nsu-budget-agent.git
   git remote -v
   git push -u origin main
   ```

   Если `origin` уже существует, сначала проверьте его; не переназначайте автоматически.
   При неожиданной удалённой истории остановитесь и разберите различия, без force push.

Основание последовательности: [GitHub: добавление локального проекта](https://docs.github.com/en/migrations/importing-source-code/using-the-command-line-to-import-source-code/adding-locally-hosted-code-to-github).

## Приглашение второго участника

Для личного репозитория откройте **Settings → Collaborators → Add people**,
найдите GitHub-логин второго участника и отправьте приглашение. Доступ появится
после принятия. Для репозитория организации управление доступом может называться
**Collaborators & teams**. Участнику нужен доступ для отправки рабочих веток.
[Инструкция GitHub](https://docs.github.com/en/repositories/managing-your-repositorys-settings-and-features/repository-access-and-collaboration/inviting-collaborators-to-a-personal-repository)

Второй участник клонирует репозиторий в собственный рабочий каталог, не внутрь
другого Git-репозитория, открывает его в VS Code и читает свой файл разработчика.
Для приватной сдачи отдельно предоставьте доступ `promsoft` и `madrugado` и
проверьте, что у жюри действительно есть доступ к дедлайну.

## Ветки и Pull Request

- `main` — согласованная интеграционная версия. Сейчас это честно обозначенный
  каркас; после S1 она должна сохранять работоспособность сквозного сценария.
- Короткие ветки: `feature/a-budget-ledger`, `feature/b-generic-solver`,
  `fix/a-usage-accounting`, `docs/shared-contracts`. Постоянная ветка `develop`
  для команды из двух человек не нужна.
- Одна ветка решает одну проверяемую задачу. Контракты выносятся в отдельный
  маленький PR, который объединяется раньше зависимых реализаций.
- На GitHub выбирайте base `main`, compare — рабочая ветка. Рано создавайте draft,
  по завершении назначайте другого участника reviewer. Описание — проблема,
  итоговое поведение, изменения контракта и фактически выполненные проверки.
- Объединяйте после проверки вторым участником. По возможности настройте защиту
  `main` с одним review; до её настройки соблюдайте тот же порядок вручную.
- CI появляется вместе с реальными проверками в A6. Пустая или пропускающая все
  тесты проверка не считается доказательством готовности.

[GitHub: создание Pull Request](https://docs.github.com/en/pull-requests/how-tos/create-pull-requests/creating-a-pull-request)

## Синхронизация без переписывания общей истории

Начинайте новую задачу с чистой рабочей копии:

```powershell
git switch main
git pull --ff-only
git switch -c feature/a-budget-ledger
```

В процессе работы коммитьте только относящиеся к задаче файлы. Для обновления
уже опубликованной рабочей ветки сначала сохраните собственную работу коммитом,
затем, оставаясь на ней:

```powershell
git fetch origin
git merge origin/main
git push -u origin feature/a-budget-ledger
```

B использует своё имя ветки. При конфликте в контракте согласуйте поведение вдвоём;
не выбирайте автоматически весь `ours` или `theirs`. После разрешения снова
выполните соответствующие проверки. При необходимости отменить незаконченный
merge используйте `git merge --abort`. Не применяйте force push к `main`.

## Общие файлы и рецензирование

`docs/contracts.md`, `src/nsu_budget_agent/contracts/`, `pyproject.toml`, будущий
lock-файл, Dockerfile и конфигурация — согласованные точки изменения. A сводит
контракты и зависимости, B рецензирует потребительскую сторону. B владеет
фикстурами, решателями и внешним оценщиком; A проверяет их интеграцию и лимиты.

Перед изменением общей границы откройте задачу с примером входа/выхода и договоритесь,
кто вносит правку. Фиксируйте решение и затронутые задачи в PR. Не держите два
параллельных определения одного объекта. Ежедневно объединяйте небольшие завершённые
изменения, а не две независимые подсистемы в последний день.

## Ключи, данные и ограничения

Каждый использует свой индивидуальный ключ NeuralDeep. Для будущей локальной
разработки предусмотрен игнорируемый `.env`; автоматического загрузчика сейчас
нет. Финальные ключи и адрес передаются окружением. Не храните секреты в URL,
тестах, скриншотах, промптах, логах или GitHub issue. Если секрет попал в Git,
сначала отзовите/замените его: удаление в следующем коммите не стирает историю.

В Git не входят `.env*` кроме пустого `.env.example`, окружения, приватные задачи,
выходные ответы, необработанные траектории, ключевые файлы и регистрационные данные.
Локальные данные — `data/local/`, результаты — `experiments/runs/`. Небольшие
собственные фикстуры можно коммитить в `tests/fixtures/` после проверки происхождения.

Обычные проверки PR не используют платный API. Живые эксперименты запускаются
отдельно с явно выбранным лимитом и учётом правил сервиса. Не передавайте ключи
друг другу и не используйте несколько аккаунтов для обхода ограничений.
