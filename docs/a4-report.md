# A4 — Task Loader + Baseline Scheduler

Реализовано в `feature/a4-planner`. Публичные DTO/Protocol A1, Ledger A2, Gateway A3
и компоненты B не изменялись. A5–A7 не реализованы. Сеть и NeuralDeep не вызываются;
commit/push/merge не выполнялись. Новых зависимостей нет.

## Реализация

- `task_io/loader.py`: DirectoryTaskLoader по порту TaskLoader; отдельные LoadIssue,
  стабильный порядок обнаружения, исключение всех дублирующихся ID.
- `task_io/adapters/organizer.py`: OrganizerTaskAdapter по TaskAdapter; task.json,
  task_id/instruction/reward, task_type (либо type) и check. Четыре подтверждённые
  метки поддерживаются, неизвестные и отсутствие метки допускаются по Contracts v1.
  Тип не выбирает код и не включает динамический импорт.
- `task_io/_files.py`, `_windows.py`: ограниченное read-only чтение, отдельные
  task_root/work_root, no-follow traversal, запрет ссылок и специальных файлов,
  сравнение идентичности каталога из stat с открытым handle, в том числе после
  discovery и для workspace, проверка идентичности файлов и метаданных. Хеши SHA-256 и размеры
  фактических байтов входят в ArtifactRef. I/O вынесен в asyncio.to_thread.
- `planning/registry.py`: StaticSolverRegistry с уникальными ID и обязательным
  generic; первое чтение закрывает регистрацию. Реальных решателей B не добавлено.
- `planning/baseline.py`: BaselinePlanner реализует чистый Planner.choose и выдаёт
  только PlanDecision с AttemptBudget. Не вызывает assess/step/LLM/SDK, не меняет
  прогресс и не пишет файлов, включая answer.txt.

Манифест разбирается как JSON, но expected не извлекается и не участвует ни в одном
решении; сырые данные манифеста не сохраняются в TaskSpec. В artifacts не попадают
manifest, expected/expected.*/expected_*, старые ответы, скрытые и служебные области.
Тесты по публичным соглашениям имён и простым командам инструкции защищены. Новые
имена/бинарные файлы допустимы без автоматического запуска или попыток парсинга.
Полные детали, пределы ввода и ограничения распознавания тестов — в README task_io.

## Baseline-стратегия

Фильтры: допустимый статус и not_before, максимум попыток/параллельности, применимость,
наличие доступных required_tools, общий дедлайн и оценки, помещающиеся в профиль и
текущий остаток A2. Unsupported одного маршрута не исключает другой.
Submitted/running/exhausted не планируются повторно. None означает отсутствие
назначения **сейчас**, в том числе временное ожидание ресурсов.

В auto для двух загруженных задач используется coverage, иначе portfolio. В coverage
первая потенциально допустимая попытка предшествует повторам, в том числе при ожидании
not_before или временно удержанных средств. Окончательно неприменимые предложения,
недоступные инструменты и явно непомещающиеся в лимиты предложения не блокируют повторы.
Нулевая награда не исключает задачу; при равных условиях порядок определяется task_id/solver_id.

В portfolio при наличии допустимой положительной награды попытка с reward=0 не получает
LLM-бюджет. Явно объявленный маршрут без LLM и изолированная нулевая задача допускаются.
Далее приоритет имеют явно объявленные в доверенной конфигурации маршруты без LLM,
затем applicability=yes перед unknown. Для известных probability и cost применяется
`reward * probability / (1 + cost_units)`; это простая эвристика, не обученная модель.
Fraction избегает float overflow и потери порядка очень больших целых наград.
Длительность учитывается фильтром по времени и как дополнительный критерий.
Неполные оценки остаются None: для них нет выдуманной вероятности или стоимости,
используются награда, имеющиеся оценки и стабильный порядок.

`deterministic_solvers` — доверенный список ID, а не вывод из reason, имени, type_hint
или expected_cost_units=0. Таким маршрутам выделяется max_llm_calls=0, max_cost_units=0,
allowed_models=(). При общем профиле max_llm_calls=0 действует тот же запрет LLM.
Это ограничение полномочий попытки, не обещание успешного решения. Для остальных
выделяется общий профиль, обрезанный текущим available_units и дедлайном; неизвестные
оценки не становятся нулём. Known estimates не выдаются за гарантированные caps.

## Граница с исполнением и расширение

Доверенный будущий код сборки может использовать существующие порты так:

```python
report = await loader.load(tasks_dir)  # В A6 tasks_dir придёт из --tasks-dir.
catalog = tools.catalog()
offers = tuple(
    solver.assess(task, catalog)
    for task in report.tasks
    for solver in registry.all_solvers()
)
planner = BaselinePlanner(tools=catalog, deterministic_solvers=deterministic_ids)
decision = planner.choose(report.tasks, offers, progress, ledger.snapshot(), config, now)
```

На этом A4 заканчивается. A5 должен пометить выбранную задачу running **до следующего
choose**, сгенерировать ID попытки, исполнить её, учесть результат, дождаться not_before
для deferred и отметить submitted только после saved/already_saved. Повтор choose с
теми же снимками намеренно возвращает то же решение. Нет внутренней очереди, которая
могла бы разойтись с TaskProgress.

После `choose -> None` независимый от Protocol помощник `next_not_before_wakeup`
повторно вызывает Planner на будущих значениях not_before и возвращает ближайшее время
с назначением при *текущем* снимке бюджета. A5 должен одновременно ждать завершения
активных попыток и изменений бюджета, включая поздний usage, и переоценивать снимки.
Возвращённый помощником `None` не означает окончательного завершения: средства могут
освободиться без будущего not_before. Общий deadline ограничивает ожидание.

AttemptBudget — верхний лимит, не денежный резерв. A2/A3 резервируют каждый запрос.
Конкурирующие попытки могут получить budget_exhausted при поздней отправке; A4 не
дублирует книгу учёта. blocked исключает LLM-маршруты, но не детерминированную работу
до общего дедлайна. Coverage задаёт порядок, не гарантирует решение двух задач при
недостаточном бюджете/времени или ошибочной оценке.

Будущий adaptive scheduler заменяет реализацию Planner с той же сигнатурой choose.
Измеренные оценки поступают через SolverOffer; маршрут и лимиты — через PlanDecision.
Model routing может менять allowed_models/их порядок из доверенного профиля, не
перенося модели в решатели и не меняя Protocol. Сейчас обучения, калибровки и
самостоятельных LLM-оценок нет. Строгий профиль NeuralDeep не подменяется mock-флагами.

Добавлены 51 тест A4: 25 загрузчика, 25 планировщика/реестра/A2 и один контрактный
сценарий C02/C11. Fake B-компоненты оценивают предложения, но их step не исполняется.

обхода, альтернативные work_root, защиту исходника

## Ограничения и оставшиеся проверки

- Реальный формат финала и новые публичные поля остаются задачей входного адаптера;
  неизвестный формат диагностируется, произвольная metadata не переносится.
- Загрузчик безопасно формирует ссылки, но не создаёт staging/ОС-песочницу. В A5/B1
  обязательна повторная проверка путей, хешей и protected при I/O; вход может измениться
  до первого stat или после возврата DTO; file ID могут переиспользоваться. Проверки
  уменьшают конкретные гонки, но не являются абсолютной гарантией при произвольной
  конкурентной модификации ФС. Альтернативный адаптер — доверенный код, не песочница.
  Произвольный код до проверенного isolation backend не исполняется.
- Отмена await не прерывает уже начавшееся read-only чтение в потоке. Оно ограничено
  локальными пределами и закрывает ресурсы, но таймаут на зависшей файловой системе
  и изоляция самого mount потребуют эксплуатационной проверки A6.
- Эвристика не гарантирует оптимального портфеля; известные оценки могут ошибаться,
  неполные предложения внутри того же класса приоритета идут после полностью оценённых.
- Файловые POSIX-проверки и полный SDK smoke нужно подтвердить в GitHub Actions;
  доступность Windows symlink не выдана за выполненную проверку.
- Сохраняются Q1/Q5 A3: единицы внешнего бюджета и подтверждение NeuralDeep bounds,
  reasoning/usage/caps. A4 использует внутренние Units и не выбирает единицы BUDGET.
