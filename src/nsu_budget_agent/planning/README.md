# Оценка и выбор — A

`StaticSolverRegistry` регистрирует явные реализации B, требует уникальные ID и
ровно один generic. Первый all_solvers/get закрывает регистрацию. Динамических
импортов из задания нет; assess вызывается доверенным кодом сборки, не планировщиком.

`BaselinePlanner.choose` — чистая функция над TaskSpec, SolverOffer, TaskProgress,
глобальным BudgetSnapshot, RunConfig и переданным monotonic now. Результат —
PlanDecision или None: последнее означает «нет назначения сейчас», а не доказанную
невыполнимость. Нет состояния очереди, вызовов step/LLM, файлового I/O и создания answer.txt.
Повтор с теми же снимками возвращает то же решение. Оркестратор A5 обязан сразу
пометить назначенную задачу running до следующего choose, а submitted — после публикации.

Стратегия:

1. Исключить no, недоступные обязательные инструменты, running/submitted/exhausted,
   not_before в будущем, исчерпанное число попыток и явно не помещающиеся оценки
   стоимости/времени. Учитывать max_parallel_tasks. Unsupported последней попытки
   исключает её решателя, но оставляет другие маршруты.
2. В auto при двух задачах выбрать coverage, иначе portfolio. В coverage первая
   попытка потенциально допустимой задачи предшествует повторам, включая ожидание
   её будущего not_before или удержанных средств. При окончательно неприменимых
   offer, недоступных инструментах и невозможности уложиться в лимиты повторы не блокируются.
   Нулевой reward не исключает задачу.
3. В portfolio, если сейчас доступна задача с положительной наградой, не назначать
   LLM-попытку с нулевой наградой. Детерминированная попытка без LLM остаётся допустимой.
   Далее предпочесть явно объявленные маршруты без LLM; затем yes перед unknown. При
   известных cost и probability сравнить `reward * probability / (1 + cost_units)`.
   Единица в знаменателе — регуляризация ранжирования, а не новая оценка расхода.
   Fraction сохраняет порядок больших целых reward и избегает float overflow.
4. При неполных оценках не вычислять ожидаемый выигрыш и не подставлять probability=1
   или cost=0. Использовать reward, затем имеющиеся cost/probability/duration;
   для равных условий предпочесть ещё не пробованный маршрут и task_id/solver_id.
   Полностью оценённые предложения внутри того же класса приоритета идут раньше неполных.
   Для равной выгоды и прочих условий меньшая известная длительность предпочтительнее.

`BaselinePlanner(tools=catalog, deterministic_solvers=(...))` получает доверенный
каталог и явные ID маршрутов без LLM. `ToolSpec.available=False` означает недоступность.
Нулевая expected_cost_units сама по себе **не** отключает LLM. Для объявленного
детерминированного маршрута (или общего профиля с max_llm_calls=0) выделяются
max_cost_units=0, max_llm_calls=0, allowed_models=(). Это ограничение исполнения,
а не придуманная оценка. Если такой offer сообщает положительную стоимость, он не помещается.

Для остальных маршрутов выделяется общий профиль, ограниченный текущим available_units
и дедлайном; известная оценка не становится гарантированным cap. Вызовы ограничены
числом шагов и профилем. Лимит попытки не резервирует деньги: общий A2 Ledger
атомарно резервирует каждый запрос через A3. Параллельные попытки могут конкурировать
за остаток и получить budget_exhausted, но не двойное списание. blocked запрещает новые
LLM-маршруты, не детерминированную работу; общий deadline запрещает оба вида.

После `choose(...) -> None` помощник `next_not_before_wakeup(planner, tasks, offers,
progress, budget, config, now)` может найти ближайшее время, когда с текущими снимками
появится назначение. Это не изменение Protocol Planner и не таймер: A5 должен также
ожидать завершения работающих попыток, изменения резерва/позднего usage и дедлайна,
затем получать новый snapshot и повторять choose. `None` из помощника не доказывает
окончательное завершение: например, удержанный резерв может освободиться позже.

Будущее расширение — другая реализация Planner с тем же choose, внешние измеренные
SolverOffer и порядок allowed_models в доверенном профиле. Адаптивное обучение,
model routing и исполнение A5 здесь не реализованы. Для реального A3 strict нужны
подтверждённые provider bounds; A4 может тестироваться исключительно с fake Solver.
