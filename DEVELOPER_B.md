# Разработчик B: инструменты, решатели и проверка качества

## Твоя цель и текущая точка

Сделать исполнителя, который получает реальные правильные ответы на разнообразных
задачах за ограниченное число действий. Твоя работа определяет вероятность успеха,
расход на неудачные попытки и способность справляться с неизвестными заданиями.

Сейчас есть только каркас и спецификация. Решатели, инструменты, зависимости
и тесты ещё не реализованы. План ниже относится к последующей разработке;
подготовка репозитория не включает API-эксперименты или обучение моделей.

## Твои каталоги и граница с A

Ты владеешь `src/nsu_budget_agent/{tools,solvers,validation}/`, `evaluation/`,
`tests/fixtures/`, правилами набора задач в `data/` и проверками качества.
Общие интерфейсы уже зафиксированы в `docs/contracts.md`; последующие изменения
`contracts/` проходят review обоих участников.

A владеет загрузкой внешнего формата, планировщиком, бюджетом, LLM-шлюзом,
openJiuwen-оркестрацией, публикацией, конфигурацией и Docker. Ты задаёшь требования
к данным и инструментам, но не создаёшь второй LLM-клиент, второй баланс или
собственную точку сохранения финального `answer.txt`.

## Contracts v1: решения уже приняты

Источник истины — [Contracts v1](docs/contracts.md). Технический S0 закрыт;
не нужно заново выбирать поля, статусы, способы отмены и границу с A. Общие
Python-определения в `contracts/models.py` и `contracts/ports.py` первым небольшим
PR создаёт A. До его слияния готовь фикстуры/тестовые сценарии и внутреннюю логику
инструментов; не создавай собственную копию DTO или интерфейсов.

| Что реализуешь | Контракт |
| --- | --- |
| Любой решатель | `solver_id: str`, sync `assess(TaskSpec, tuple[ToolSpec, ...]) -> SolverOffer` |
| Один шаг решения | async `step(SolverContext, tuple[StepRecord, ...]) -> SolverStep` |
| Инструменты | sync `catalog() -> tuple[ToolSpec, ...]`; async `execute(call_id, ToolCall, ToolContext) -> ToolResult` |
| Локальная проверка | async `validate(TaskSpec, AttemptResult, ToolContext) -> ValidationResult` |

SolverStep — ровно ToolCall, CandidateAnswer или StopAttempt. В одном step допустим
один complete через LLMSession A. **Внешнего цикла в решателе нет:** вызов инструментов,
переход к следующему шагу, отмену и создание AttemptResult выполняет JiuwenAdapter A.
Решатель stateless, его история — переданные StepRecord. assess чистый: без I/O и LLM.

Инструменты работают только в staging, ограничены ToolContext и не публикуют ответ.
Первичные protected-пути задаёт загрузчик; инструмент тестов защищает обнаруженные
тестовые пути до запуска и сообщает их A. Код выполняется только при проверенной
изоляции; иначе инструмент недоступен. Не обещай защиту исходных manifest одним cwd.

Validator получает замороженный кандидат/snapshot. Проверки формата, путей и
защищённых файлов blocking; отсутствие семантического оракула — nonblocking
inconclusive. Если требуются доступные тесты, их прохождение blocking. A принимает
только результат без failed и с passed у всех blocking-проверок. Ты не объявляешь
скрытые тесты пройденными, не меняешь бюджет и не возвращаешь SubmissionReceipt.

Начальный интеграционный сценарий фиксирован: незнакомая метка типа, текстовый
артефакт с новым именем, одно чтение и строковый ответ. LLM-double сначала выдаёт
ToolCall, затем CandidateAnswer. Эталон хранится только во внешнем тесте; нужен
также вариант без workspace. API для этой проверки не требуется.

## Последовательность и задачи

### B1. Подготовить общий набор ограниченных инструментов — P0, ограничения P1

- **Назначение:** дать решателям надёжный доступ к артефактам и вычислениям.
- **Результат/пути:** `tools/`, `tests/unit/`, `tests/contracts/`, небольшие фикстуры.
- **Зависимости:** Contracts v1 уже определяет интерфейсы; A1 нужен только для общего импорта.
  Подготовка матрицы, fixtures и внутренней логики не ждёт LLM-шлюза.
- **Работа:** перечисление и ограниченное чтение файлов, поиск текста, структурированное
  выполнение вычислений, применение правок и запуск проверок. Читатели выбираются
  по формату/возможности, а не по именам учебных файлов. Неизвестный формат возвращает
  диагностируемую неподдерживаемость. Новые читатели добавляются по реальной потребности.
- **Приёмка:** [ ] чтение не выходит за разрешённые корни, в том числе через symlink;
  [ ] ошибка, пустой ответ и усечённый вывод различаются; [ ] лимиты чтения, времени
  и вывода действуют; [ ] дочерние процессы не получают ключ API;
  [ ] тестовые файлы защищены от правки; [ ] отмена не оставляет бесконечные процессы;
  [ ] произвольный код запускается только проверенным изолирующим backend, иначе
  инструмент unavailable; [ ] `cwd` не объявлен полной песочницей.

### B2. Реализовать stateless общий решатель — P0

- **Назначение:** предлагать следующий шаг для задачи без известного алгоритма.
- **Результат/пути:** `solvers/generic/`, проверки C02/C07; generic зарегистрирован
  через реестр A и реализует тот же Protocol, что и специализации.
- **Зависимости:** A1 для импортов; fixtures и LLM-double позволяют работать без A3/A5.
  B1 нужен для реального исполнения действий, но не для unit-проверки step.
- **Работа:** чистая оценка применимости и async step по контексту/истории.
  Преобразовать текстовый JSON LLM в один ToolCall, CandidateAnswer или StopAttempt;
  native tool calling API не требуется. Не исполнять ToolCall внутри step.
- **Приёмка:** [ ] неизвестный type_hint не отключает generic;
  [ ] максимум один complete на step; [ ] malformed/truncated JSON не исполняется;
  [ ] ответы инструментов с ошибками/усечением учитываются;
  [ ] нет состояния другой задачи в экземпляре решателя;
  [ ] одинаковая история позволяет повторить unit-проверку без SDK;
  [ ] внешний цикл, лимиты и AttemptResult принадлежат A.

### B3. Добавить экономичные специализации — P0 для базовых примеров, развитие P2

- **Назначение:** сократить стоимость там, где доступен надёжный специализированный путь.

### B4. Проверка кандидатов и диагностика препятствий — P0, надёжность P1

- **Назначение:** отличить готовый результат от ошибочного формата и необоснованного отказа.
- **Результат/пути:** `validation/`, ValidationResult/CheckResult и проверки C08/C09.
  AttemptResult строит A; свидетельства кандидат передаёт через CandidateAnswer.
- **Зависимости:** B1, A1; тестовый AttemptResult со snapshot позволяет реализовать validate
  до A5. A5 затем применяет фиксированное правило AcceptanceDecision.
- **Работа:** проверять ответ по требованиям задания, выполнять доступные тесты,

  `exact_int/exact_str/unittest` из примеров не считать исчерпывающим перечнем.
- **Приёмка:** [ ] runtime не читает `expected` ни напрямую, ни через инструмент;
  [ ] неподдерживаемость, отсутствие прогресса, ошибка инфраструктуры, исчерпание

  [ ] один неудачный поиск или тест не объявляет задачу невыполнимой;
  [ ] ограниченность локальной проверки видна A;
  [ ] `DONE` предлагается только по требованиям coding-задачи с нужными артефактами;
  [ ] решатель не пишет финальный ответ в обход общего модуля публикации.

## Как работать независимо и интегрироваться

Порядок: Contracts v1 → B1/B5; после раннего A1 — B2 и B4, затем B3.
B2 тестируется на LLM-double, B4 — на готовом AttemptResult, без ожидания A5.
B6 растёт вместе с интеграцией; B7 не блокирует сдачу.

До A1 готовь матрицу сценариев и фикстуры C02/C03/C08/C09, не дублируй определения.
После A1 импортируй общие типы и реализуй Protocol. От A ожидаются ранний PR этих
определений, LLMSession-double и ToolContext; рабочий SDK не является зависимостью B2.
Передай A готовые Solver.assess/step, ToolExecutor и Validator с контрактными тестами.
После A3/A5 тот же интерфейс подключается к реальному исполнителю без нового клиента. Каждый новый инструмент передавай A
с описанием входа/выхода, ошибок, ограничений и соответствующими тестами.
Новый формат сначала обсуждается как расширение читателя/адаптера, а не как
новый обязательный тип задачи в планировщике.

## Регламент, о котором отвечаешь прежде всего ты

Финальный набор неизвестен; восемь примеров не задают потолок сложности.
15–25% невыполнимых — ориентир, не обязательная доля отказов. Никаких локальных
нейросетевых моделей или загрузок при запуске. LLM только через шлюз A к четырём
разрешённым Qwen; планирование тоже оплачивается. Инструменты работают без GPU
при ограниченных CPU/RAM/времени. Изменять тесты запрещено. Ответы и исправления
должны быть сохранены после каждой задачи через A. Ключи не передаются процессам
задач, в Git и второму участнику. Доступ API до 20 ноября не подтверждает дедлайн.

## Git и критерий передачи

Начинай от обновлённой `main`: `git switch main`, `git pull --ff-only`,
`git switch -c feature/b-generic-solver`. Одна небольшая задача — одна ветка и PR
в `main`, reviewer A. Изменение общего контракта согласуй до реализации и вынеси
в отдельный ранний PR. Для синхронизации сохрани работу коммитом, затем
`git fetch origin`, `git merge origin/main`; проверь поведение после конфликтов.
Не делай force push в `main`. Первая публикация — по `docs/collaboration.md`.

Не коммить `.env`, ключи, приватные задачи, ответы запусков, большие датасеты,
окружения и сырые логи. Малые собственные фикстуры должны иметь понятное происхождение.
В PR укажи задачу, вход/выход, результаты проверок и что осталось неизвестным.
Изменение документации не требует живого API.
